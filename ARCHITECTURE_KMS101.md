# KMS101 – Project Context for AI Assistants

This repository contains a **Key Management Service (KMS)** proof of concept
plus a **data service** that uses the KMS via envelope encryption.

The goal is to simulate a realistic cloud KMS setup with a clean separation of
concerns between **key management** and **data storage / encryption**.

Current implementation status:
- KMS FastAPI implements in-memory CRK create/rotate and DEK generate/unwrap endpoints using AES-GCM wrapping (real crypto; no Postgres yet).
- Data service FastAPI calls KMS, performs AES-GCM data encryption/decryption, and stores records in memory (no Postgres yet).
- Real crypto is in place; persistence and rotation logic remain to be added.

## Big Picture

There are 3 main services:

1. **KMS Service (FastAPI, port 8000)**
   - Manages key material and performs cryptographic operations.
   - Owns all logic around:
     - Master key (MK)
     - Customer root keys (CRK / CMK / KEK)
     - Data encryption keys (DEK)
   - Provides an HTTP API for:
     - Creating / rotating CRKs
     - Generating DEKs wrapped under a CRK
     - Unwrapping DEKs so the data service can decrypt data

2. **Data Service (FastAPI, port 8001)**
   - Simulates an application that stores customer data.
   - Does NOT manage long-term key material itself.
   - For each piece of data:
     - Requests a DEK from the KMS.
     - Encrypts data locally with that DEK using AES-GCM.
     - Stores ciphertext + wrapped DEK + metadata (currently in-memory; later Postgres).

3. **Database (PostgreSQL, port 5432)**
   - Stores:
     - Encrypted data records (ciphertext, nonce, tag, etc.)
     - Wrapped DEKs and key metadata
   - The KMS will also store CRK metadata and wrapped CRKs here.

Communication:

- `data-service` ⇄ `kms-service` over HTTP inside docker-compose network
- `data-service` + `kms-service` ⇄ `db` over TCP

## Key Hierarchy / Cryptographic Design

The design uses **envelope encryption** with several layers:

1. **Master Key (MK)**
   - Root key for the KMS instance.
   - Used only to encrypt/decrypt **Customer Root Keys (CRK)** at rest.
   - In this PoC, derived from `MASTER_KEY_PASSPHRASE` env variable
     using a KDF (e.g., PBKDF2 or Argon2).
   - Stays only in memory after derivation.

2. **Customer Root Key (CRK) / Key Encryption Key (KEK)**
   - One (or more) per customer/tenant.
   - Used to wrap (encrypt) **DEKs**.
   - Stored in the database **encrypted under the master key**.
   - Rotatable with versions (v1, v2, etc.).

3. **Data Encryption Key (DEK)**
   - Random symmetric key used to encrypt actual application data.
   - Generated by the KMS.
   - Used with an AEAD algorithm (AES-256-GCM or ChaCha20-Poly1305).
   - Stored only in wrapped form (encrypted under a CRK).
   - Plaintext DEKs exist only in memory for the duration of an operation.

Layers:

- **MK** → encrypts CRKs
- **CRK** → encrypts DEKs
- **DEK** → encrypts data

The data service never sees MK or CRKs. It only sees:

- Plaintext DEKs (in memory during operations)
- Wrapped DEKs (stored in DB)

## Planned KMS API (FastAPI)

We plan to implement the following endpoints in `kms-service`:

1. `POST /v1/customers/{customer_id}/root-keys`
   - Purpose: create or rotate a Customer Root Key (CRK).
   - Steps:
     - Generate random CRK bytes.
     - Encrypt CRK with MK (AES-GCM) → `crk_ciphertext_under_mk`.
     - Store in DB with metadata: `crk_id`, `version`, `status`, `algorithm`.
   - Returns: CRK metadata (no plaintext).

2. `POST /v1/deks:generate`
   - Purpose: generate a new DEK for a given customer/CRK.
   - Request: `{ customer_id, crk_id, dek_algorithm, data_context }`.
   - Steps:
     - Load & decrypt CRK using MK.
     - Generate random DEK bytes.
     - Encrypt DEK with CRK → `wrapped_dek`.
   - Returns:
     - `plaintext_dek` (base64) for immediate use by data service
     - `wrapped_dek` object with metadata (crk_id, crk_version, algorithm)

3. `POST /v1/deks:unwrap`
   - Purpose: unwrap an existing wrapped DEK (for decrypt operations).
   - Request: `{ wrapped_dek, purpose, data_context }`.
   - Steps:
     - Load & decrypt CRK using MK.
     - Decrypt wrapped DEK with CRK.
   - Returns:
     - `plaintext_dek` (base64)

In early iterations we may mock crypto (e.g., pass-through) and later
swap in real AES-GCM using the `cryptography` library.

## Planned Data Service API (FastAPI)

In `data-service`, we plan endpoints like:

1. `POST /data`
   - Purpose: store a new piece of customer data.
   - Flow:
     - Call KMS `/v1/deks:generate` to get `{ plaintext_dek, wrapped_dek }`.
     - Encrypt data locally with `plaintext_dek` using AES-GCM.
       - Generate a random nonce/IV.
       - Compute ciphertext + auth tag.
     - Store in DB (currently in-memory dict; later Postgres):
       - `customer_id`
       - `ciphertext`
       - `nonce`
       - `tag`
       - `wrapped_dek` (JSON or columns)
   - Response: an object ID (e.g., `data_id`).

2. `GET /data/{id}`
   - Purpose: retrieve and decrypt existing data.
   - Flow:
     - Load record from DB by `data_id`.
     - Extract `wrapped_dek`, `ciphertext`, `nonce`, `tag`.
     - Call KMS `/v1/deks:unwrap` with `wrapped_dek`.
     - Use returned `plaintext_dek` with AES-GCM to decrypt ciphertext.
    - Response: plaintext data (or structured JSON).

## Implementation Priorities

1. **Plumbing first (done):**
   - Docker Compose with `kms-service`, `data-service`, `db`.
   - Health endpoints at `/health` for both services.

2. **Basic in-memory KMS logic (done):**
   - CRK and DEK endpoints in KMS with in-memory storage and AES-GCM wrapping.
   - Data endpoints call KMS, AES-GCM encrypt/decrypt, and store data in memory.

3. **Persistence (next):**
   - Add SQLAlchemy models for:
     - CRKs
     - Encrypted data objects, including wrapped DEKs
   - Store everything in Postgres.

4. **Extras (if time):**
   - Key rotation logic.
   - Simple audit logging.
   - Basic auth/mTLS for KMS calls.

## Coding Style / Expectations for AI

When generating code in this repo, please:

- Respect the service boundaries:
  - All key-wrapping logic belongs in **kms-service**.
  - Data encryption/decryption logic belongs in **data-service**, but
    it should always obtain DEKs from KMS.
- Use:
  - FastAPI
  - Pydantic models for request/response schemas
  - The `cryptography` library for crypto (no custom crypto).
- Prefer clear, explicit functions with docstrings describing:
  - Which key level they operate on (MK, CRK, DEK).
  - Whether they are doing wrap/unwrap or encrypt/decrypt data.

The main objective is to demonstrate a clean envelope encryption
implementation with a realistic microservice separation suitable for a
cloud/cybersecurity portfolio project.
